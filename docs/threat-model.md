# Threat model: single-dispatcher logistics prototype

Protected assets are the dispatcher's approval authority, parcel custody, courier capacity, one assignment per incident, private credentials and the integrity of evidence. Data and events are synthetic. This is an educational prototype, not a production dispatch service.

Entry points are authenticated record views and POST investigation, decision, commit and simulated-event routes. All record views require HTTP Basic credentials. Every write requires the exact configured Origin; absent, null and other origins are rejected. HTML notes are escaped. A restrictive content-security policy disables scripts and framing. Responses are not cached. Request bodies are limited to 8 KB and typed records reject extra fields. The authenticated identity comes from server credential validation, never a supplied operator field.

The model can request only five read tools. They retrieve records scoped to the incident or the shared depot's couriers. Proposal and escalation declarations do not authorize writes. The service independently validates custody, availability, capacity, deadline, price, quote expiry and cited record versions. An immutable proposal needs an authenticated stored approval. Commit checks approval ownership and rechecks all facts in a single transaction. A unique incident assignment and stable operation ID prevent repeat booking. Simulated pickup and delivery are ordered, owned by the approving operator, and idempotent by event ID.

Credentials are private environment settings, hidden in configuration representations. The provider key is sent only to the fixed HTTPS OpenRouter endpoint in its authorization header; redirects are disabled. Secrets do not enter model context or business audit entries. Raw provider errors are replaced with a generic code. Untrusted notes can still influence a model's proposal or cause a denial of useful service; prompt wording is not the approval boundary. Audit entries and graph checkpoints contain synthetic notes and model outputs, so they must be treated as private data if real information is introduced.

Run locally on loopback with one worker. Remote Basic authentication requires HTTPS and the configuration rejects remote HTTP origins. Config validation does not install TLS, a firewall, authentication rate limiting or a reverse proxy. Deploying publicly needs a separately reviewed hosting configuration. The graph's incident lock is process-local; multiple workers/processes are outside this deployment scope. SQLite transactions still protect business assignment uniqueness.

Remaining limits: one dispatcher, no account recovery, no role management, no distributed graph lock, no arbitrary integrations, no production courier webhook verification, no tamper-proof audit sink, and no live model behavior measured yet. Per-incident inference attempts are bounded; a provider account spending limit is also needed before live use. Security assertions apply only to the tested scenarios.

Verification: 19 checks in tests/test_adversarial.py passed, including credential/field forgery, cross-incident proposal use, stale approvals, forbidden tools, hostile notes, secret sentinels, a successful authorized control and detection of an explicitly faulty approval-bypass double. Existing HTTP/recovery tests additionally exercise origin, HTML escaping, rollback, response loss and repeat events. The hostile model and faulty double are deliberate test inputs, not naturally occurring agent defects. This suite is not a penetration test or security certification.
